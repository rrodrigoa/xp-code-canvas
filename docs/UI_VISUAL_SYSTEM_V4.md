# XP Python UML Canvas — V4 visual design, structural zoom and Sankey lens

**Implementation:** `src/webview`, `src/shared/semanticVisuals.ts`, `src/shared/flowLens.ts`.
**Scope:** Non-AI enhancements layered on V3. The previous V2 semantic graph/worker, V3 UML/Git, file focus and native-editor experience remain the source of truth.

## Research and interpretation

References inspected 2026-11-19:

- Etchpad, https://www.etchpad.ai/ — screenshots show containment-colored class/file/module blocks, semantic levels, focused caller/dependency navigation, Git semantic-diff overlays, and source reading at close zoom.
- CodeCanvas, https://www.codecanvas.app/ and https://www.codecanvas.app/docs/getting-started/introduction — file-code panels on spatial canvas, language-server connections and zoom-dependent detail.
- blockviz, https://github.com/BlueBlazin/blockviz — nested representations of code constructs and navigation into dependencies at successively closer scales.
- CodeSee, https://docs.codesee.io/docs/explore-your-map — direct manipulation and source navigation on code maps.
- Microsoft Research Code Canvas, https://www.microsoft.com/en-us/research/wp-content/uploads/2010/07/p48-deline.pdf — semantic zoom, stable spatial organization, automatically assisted layouts.
- d3-sankey, https://github.com/d3/d3-sankey — a Sankey link's width is proportional to a **specified quantitative value**.
- ELK layered layout, https://eclipse.dev/elk/documentation/ — collision/crossing reduction; retained from V3.

We are **not copying** Etchpad's product or UI assets. This is a distinct VS Code-native implementation driven by our own Python semantic graph. It also does not integrate the AI functionality in `specs/AI_DEFERRED.md`.

## Unambiguous visual channels

| Meaning | Primary channel | Secondary channel | Constraint |
|---|---|---|---|
| Module/package container | Purple role stripe / icon | `«module»` stereotype, folder contour | Does not imply Git state |
| Class | Amber role stripe / square icon | UML class name / fields/methods | Inheritance remains a hollow UML triangle |
| Callable (function/method) | Blue role stripe / function icon | Signature, static links | No runtime hot-path inference |
| Data/property | Green chips / property icon | Attribute name and type | Unlocated fields are visibly read-only chips |
| External/unresolved | Neutral role color | Dashed/uncertain connection | Never fabricate a resolved target |
| Added/modified/removed | Separate Git accent + labeled status | Change icon / dot | Not color alone; preserved from V3 |
| Confidence / ambiguity | Opacity, dashed topology + text | Source evidence on selection | Do not equate ambiguity with Git changes |
| Sankey relationship amount | Ribbon **width** | Numeric count & accessible table | Static relationship sites, not traffic |
| Manual spatial state | Pinned node location | Pin control | Preserve on zoom, save and file focus |

All palette references are theme variables first (`--vscode-charts-*`, `--vscode-gitDecoration-*`, `--vscode-focusBorder`). Respect light/dark/high contrast and reduced motion.

## Four levels of semantic zoom

The top toolbar abstraction (`Architecture / Packages / Modules / Code`) remains **independent** from magnification and uses the same graph source.

| Effective zoom | Tier | Node content |
|---|---|---|
| below 0.64× | 0 · index | Compact card with colored, noninteractive construct strips |
| 0.64–1.12× | 1 · UML | Classic compartments (class operations/attributes, signatures) |
| 1.13–1.87× | 2 · anatomy | Source-ordered blocks for real declarations, counts, CSS size informed by source-span ratios, read-only attribute chips |
| at least 1.88× | 3 · source | Selected node expands into scrollable, syntax-highlighted **real** code from the source repository. Other nodes stay at anatomy tier to avoid a large preview-fetch storm. |
| any zoom, manual Expand | 3 | Explicit source preview for one card; card stays connected to its UML edges |

Unlocated class fields are shown as nonclickable inventory chips rather than fabricating positions. Clickable blocks correspond only to known indexed declarations. Selecting a method block expands method-level nodes when needed and reveals original graph connections. Source code is never editable within these boxes; **Open in Editor** uses the standard native VS Code editor in the same editor group, and **Return to Canvas** restores the view.

Regular wheel scrolls vertical canvas space or source preview under the cursor. **Ctrl/Cmd+wheel** zooms around the pointer anywhere (including source). Dragging a card moves the card; blank-canvas drag pans; the toolbar provides explicit zoom/fit controls.

## Structural grouping and layout

The V2 canonical graph remains separate from its V4 visual projection. A construct's sub-blocks are generated by `summarizeStructure()` from indexed children or real aggregated graph membership. The UI builds a shared `createStructureIndex()` per canonical graph revision rather than rescanning every relationship for every card. The visual never creates new semantic relationships; it only represents existing ones.

- Top-level symbols follow source order in file-focus mode.
- Existing ELK auto-layout remains active at workspace level. Focused file occupies a center lane with callers and dependencies to the sides.
- Node sizing reserves additional room for anatomy and source tiers; auto-layout runs when tier thresholds change, not on every wheel tick.
- Read-only file boundary frames use the same pan/zoom transformation as React Flow and never intercept mouse input.
- Manual/pinned positions override generated positions.
- Relationship labels remain hover/contextual to avoid dense text collisions, with selected-node relations surfaced automatically.

**Known limitation:** global auto-layout and large manually pinned clusters can still overlap. The V4 code sizes its new representations but does not yet include constraint-based postprocessing for arbitrary pinned collisions. Do not claim that all possible graphs are overlap-free.

## Sankey relationship lens

Choose **Flow** next to **UML** in the existing toolbar. It covers the same canvas tab; there is no permanent extra panel. Selecting another relationship kind or a peer node recalculates the lens. Returning to UML preserves the source graph, code navigation, file focus and layout state.

The model `buildFlowLens()` takes the exact visible graph at the selected abstraction level. It visualizes one-hop **incoming** and **outgoing** relations around the focused symbol, with no implied transitive execution route:

- Calls: counted static call sites when evidence is present, otherwise aggregated graph counts/one per known relationship.
- Imports: counted static import relationships; not bytes or package popularity.
- References/Creates: separately selectable kinds; never summed into a single ambiguous metric.
- Two-sided totals, denominators and percentages are calculated from the current **projected graph and relation type**, not from a profiler.
- Ribbon thickness proportional to the static count; tooltips and an accessible data table repeat all values.
- Multiple edges for one peer are combined; duplicate callsite evidence coordinates are deduplicated.
- Self-loops are reported but not rendered as fake throughput ribbons.
- The lens shows only one hop, so graphs with cycles are valid without introducing fictitious paths.
- At most nine peers per side plus a clearly labeled, nonclickable "more" aggregate preserve legibility.
- Uncertain references are rendered with reduced opacity/dashes, not as confirmed edges.

For **actual runtime Sankey flow**, a separate instrumented profiler/tracing dataset and explicit units would be required; no such metrics are invented here. A more advanced end-to-end, cycle-aware whole-project Sankey is a future non-AI enhancement, not delivered in V4.

## Accessibility and interaction acceptance

1. All clickable construct blocks have accessible labels and keyboard activation. Compact overview strips are noninteractive.
2. All Sankey peer bars use Enter/Space to navigate; numeric relationships are also present in an accessible table.
3. No meaning is conveyed solely by hue; type name, class icon, status text and numeric counts remain available.
4. V4 reuses native-editor navigation, selection, Git comparison, source previews and existing user-configured zoom/pins.
5. Auto layout is refreshed on tier changes and file focus, without moving manually pinned nodes.
6. Test both dark/light/high-contrast VS Code themes in a real extension host; do not substitute static HTML previews for E2E results.
